**Read `docs/status.md` first.** It is a one-page ledger of what is already built, what is

**Update it in the same commit as the work it describes.** A stale ledger is worse than none,
because it still gets trusted.

## What this is

Better Audio (released as "Voyage") is a native Android audiobook player: it scans a local folder for audio files, organizes them into books, **series**, and authors, plays multi-file books (and whole series) as one resumable timeline, tracks per-book resume position, and integrates with the lock screen, a home-screen widget, and (optionally) Gemini AI for auto-generated synopses. Single Gradle module (`app/`), package `com.betteraudio`. Kotlin + Jetpack Compose + Media3 + Room + Hilt, MVVM. `minSdk = 26`, `compileSdk`/`targetSdk = 36`.

## Build / run / deploy

The custom `gradlew.bat` is **not** the stock wrapper script — its box-drawing comment characters get mis-parsed by `cmd.exe`, so `./gradlew`/`gradlew.bat` often fail with `ClassNotFoundException: GradleWrapperMain`. Always invoke the wrapper jar directly:

```powershell

$java = "$env:JAVA_HOME\bin\java.exe"
Set-Location 'D:\code\better audio'
& $java "-Dorg.gradle.appname=gradlew" `
    -classpath "D:\code\better audio\gradle\wrapper\gradle-wrapper.jar" `
    org.gradle.wrapper.GradleWrapperMain :app:compileDebugKotlin --console=plain
```

From the Bash tool, the equivalent one-liner (used throughout this repo):
```bash
cd "D:/code/better audio" && export JAVA_HOME="C:\Program Files\Android\Android Studio\jbr" && \
"$JAVA_HOME/bin/java.exe" -Dorg.gradle.appname=gradlew \
  -classpath "D:\code\better audio\gradle\wrapper\gradle-wrapper.jar" \
```

Common tasks: `:app:compileDebugKotlin` (fastest error check), `:app:assembleDebug` (installable APK at `app/build/outputs/apk/debug/app-debug.apk`), `:app:installDebug` (install on connected device), `:app:testDebugUnitTest` (JUnit tests under `app/src/test/`).

The dev device may be attached over USB or wireless debugging; if `adb devices` is empty, ask the user to reconnect. ## Releases & channels

- **Beta APKs** are GitHub **pre-releases** (`--prerelease`, `--target beta`); **stable APKs** are standard releases (`--latest`, `--target main`). Historically both were built with `:app:assembleDebug` since the `release` variant was unsigned and Android rejected it. As of G4-5, `:app:assembleRelease` is a real, signed, R8-minified build (signing config reads `VOYAGE_RELEASE_STORE_FILE`/`_STORE_PASSWORD`/`_KEY_ALIAS`/`_KEY_PASSWORD` from `local.properties`, gitignored; keystore lives at `keystore/voyage-release.jks`, also gitignored — regenerate both if missing, there's nothing to recover). Its signature is **different from every previously-shipped debug-signed APK**, so the first release cut from it will break in-place updates for existing installs (uninstall required once). Attach the APK renamed `Voyage-<version>.apk`. `gh` is at `C:\Program Files\GitHub CLI\gh.exe`; repo is `TheEnderizer/voyage`.
- **Archive `mapping.txt` for every release build.** `:app:assembleRelease` writes `app/build/outputs/mapping/release/mapping.txt`, R8's class/method/line rename table for that exact build. Without it, a crash trace captured by `AppLog` (or shared by a beta user) reads `at a.b.c.d(SourceFile)` and cannot be resolved back to real source, even with `-keepattributes SourceFile,LineNumberTable` in place. After every `assembleRelease`, copy it out as `mapping-<versionCode>.txt` (e.g. into a local `mapping/` folder, gitignored — it's per-build and not source) before the next build overwrites it. To resolve a trace later: `retrace mapping-<versionCode>.txt trace.txt` (R8's `retrace` ships in the Android SDK build-tools).
- **Version naming decides the channel at runtime**: beta `versionName` ends in `b` (e.g. `1.7.1b`); stable does not (e.g. `1.7`). Never omit the `b` on a beta build. Bump `versionCode` on every release. As of this writing: stable = **1.7** (code 38), beta = **1.7.1b** (code 39).
- **`data/update/UpdateChecker.kt`** reads `installedVersionName()` from the PackageManager at runtime. A `b` version → beta channel (only prereleases); otherwise → stable. It fetches `/releases?per_page=30` and selects the **highest semantic version** for that channel that has an APK asset — NOT the first entry. This is deliberate: GitHub orders `/releases` by `created_at` (the tag's commit date, not publish date or version), so a release cut from an older tag sorts low; the old "take first prerelease" logic silently missed newer releases. When cutting a release, create a **fresh tag on the current HEAD** so its `created_at` is now.
- Branch workflow: develop on **`beta`**; **`main`** is fast-forwarded/merged from beta only when making a stable release. (Both currently point at the same v1.7 commit.) `changelog_beta.txt` / `changelog_stable.txt` (in `res/raw/`) are shown in Settings → About, picked by the version suffix; add a top entry per release, Keep-a-Changelog format.

## Storage model

Full-filesystem access via `MANAGE_EXTERNAL_STORAGE` and plain `java.io.File` paths — no SAF/`DocumentFile`/tree URIs. Paths are stored in the DB (`Book.folderPath`, `AudioFile.filePath`, `Book.coverArtPath`).

**Disk is the source of truth; Room is a query cache.** Everything precious about a book — overrides, synopsis, status, progress, bookmarks, sessions, skip events, its cover — is mirrored into a visible `data/` folder inside that book's own directory (`data/book.json` + `data/cover.<ext>`, or `data/<slug>.json` for one member of an AUTO cluster). Library-wide data (presets, authors, series, settings, widget designs) is mirrored into `<libraryRoot>/.voyage/`. Both get a `.nomedia`. The point is reinstall-proofing: after a delete + reinstall the user picks the same folder, `LibraryBootstrapper` detects `.voyage/settings.json` and **skips the whole first-run setup**, and the scan reads each book's doc back. See `data/diskstore/` — `BookDataPaths` (pure path derivation; `folderPath` is opaque, never `File()` it directly), `BookDataStore`/`LibraryDataStore`/`WidgetsDataStore`/`SettingsFileStore` (the stores), `DiskMirror` (the single choke point every repository write hooks into — `markDirty` for high-frequency playback writes, `flushBook`/`flushLibrary` for user edits, `suppressed { }` for bulk applies — which nests, is safe across concurrent coroutines via `SuppressionGate`'s **counter** (never make it a flag — `SuppressionGateTest` pins why), defers *every* flush path including `flushDirty` while active, and drains once on the outermost exit, so callers don't have to flush afterwards), `RestoreOps` (`ApplyMode.FRESH_IMPORT`/`MERGE`/`FORCE`), and `DiskExportMigration` (the one-time pass that back-fills existing installs). **All flush/store entry points dispatch to `Dispatchers.IO` themselves** — callers are routinely Main-dispatched ViewModel scopes.

Cover art therefore lands in `<bookFolder>/data/cover.<ext>` for every source (gallery pick, online search, embedded extraction, epub), and series/author covers in `.voyage/covers/{series,author}_<slug>.jpg` keyed by **name** (ids aren't stable across a reinstall). Legacy locations (`cover.png` dropped in the folder by the user, pre-redesign `.cover.jpg`/`.cover_<stem>.jpg`) are still **detected in place, never migrated** — see the 5-rule priority chain in `AudioFileScanner.importBook`, where a doc-recorded `source == "user"` cover deliberately outranks a stale `cover.png`. `coverFxPath` stays derived in `filesDir/cover_fx/` and is never mirrored. `LibraryRestructurer` moves whole folders (so `data/` travels with them) and rewrites the DB paths; it runs inside `DiskMirror.suppressed`.

## Architecture

### Data layer (`data/`)

**Room DB** `betteraudio.db` (`data/db/AppDatabase.kt`), **version 22**. `fallbackToDestructiveMigration()` is the safety net but **write explicit migrations** and register them in both `AppDatabase.kt` and `di/AppModule.kt`. A present-but-wrong migration crashes on launch (Room validates the resulting schema); it does NOT fall back destructively. `exportSchema = true` + `ksp { arg("room.schemaLocation", "$projectDir/schemas") }` in `app/build.gradle.kts` are permanent, not a toggle — every version's schema is committed under `app/schemas/com.betteraudio.data.db.AppDatabase/<v>.json` (starting at v19; earlier versions were never exported and cannot be retroactively produced). To verify a hand-written migration: build `:app:kspDebugKotlin` and diff your `CREATE TABLE`s against the newly generated `<v>.json` (Room compares columns by name/type/nullability, not ordinal, so an `ALTER TABLE ADD COLUMN` at the end is fine).

Entities: `Book`, `AudioFile`, `PlaybackProgress`, `Chapter`, `Bookmark`, `AudioPreset`, `ListeningSession`, `SkipEvent`, `Series`, `AuthorMeta`. (The old join-group feature — `BookGroup`/`BookGroupMember`, `Book.groupId`/`manualGrouping` — was fully removed in migration 17→18; series membership via `Book.seriesId` has been the real grouping mechanism since v12.)

**First-class Series (the core of the current design):**
- `Series` — id, name, `author?`/`narrator?` and nullable cascade defaults (`playbackSpeed?`, `boostDb?`, `eqBandsJson?`, `skipSilenceEnabled?`), plus its own `coverArtPath?`/`coverFxPath?`/`description?`. `AuthorMeta` — keyed by author name, holds a per-author `coverArtPath` (authors are a lightweight cover-only grouping).
- `Book.seriesId` (indexed, no hard FK; integrity managed in the repo) is the source of truth for membership; `seriesName`/`seriesOrder` are kept as a denormalized cache. **Never write the cache alone** — there is no cache-only DAO writer, and `BookDao.setSeriesMembership` is the single membership write. Free-text series names (Book Options / Book Info / the player) go through `SeriesRepository.setBookSeriesByName`, which resolves-or-creates the `Series` row: blank detaches (pruning the row only once nothing points at it), an existing name joins that series case-insensitively, a new name renames in place when the book is its series' sole member, and otherwise moves just that book. `VoyageApp.repairOrphanedSeriesMembership` is the one-shot repair for installs that predate this (books with a `seriesName` and no `seriesId`).
- `SeriesRepository` owns series CRUD, membership (`getOrCreateSeriesByName`, add/remove/reorder via `seriesOrder`), cover/cascade setters, and `getAudioFilesForBooks` (flatten for playback). `AudiobookRepository` is the DAO gateway for everything else — **except the widget subsystem** (`ui/widget/WidgetEditorViewModel`, `ui/widget/WidgetGalleryViewModel`, `ui/widget/WidgetImageFiles`), which injects `WidgetDesignDao`/`WidgetBindingDao` directly; there is no `WidgetRepository` and adding one would be near-pure boilerplate for that self-contained CRUD surface, so this is a deliberate, sanctioned exception rather than a gap to close.

**Cascade resolution** — `playback/AudioCascade.kt` resolves a member book's effective audio: a per-book value that differs from neutral (speed ≠ 1.0, boost ≠ 0, non-null EQ, skip-silence on) wins; else the series default; else the **global default preset**; else the scalar fallback. This is a deliberate heuristic that avoids an override-flag migration. Series **author/narrator** are propagated onto the member books (written to `authorOverride`/`narrator`) when Series options are saved, so they show everywhere — and grouping/queries use the **effective** author (`displayAuthor` = `authorOverride ?: author`; some queries use `COALESCE(authorOverride, author)`), not the raw scanned author.

**Audio presets** (`AudioPreset`) are unified **bundles** (speed + boost + EQ together); the `type` column is inert legacy. Exactly one preset can be `isDefault` — it is the **global default** fed into `AudioCascade` at play time (in `PlayerViewModel.play()`, `SeriesPlayer`, and `HomeViewModel.playResumeBook`), so it applies to every book unless the book overrides it. Managed in Settings → Audio presets (full CRUD) and the player's `AudioSettingsSheet` (save/apply the whole bundle). There is no longer a standalone "default speed" setting — it lives in the default preset.

**`SettingsStore`** wraps DataStore. Each key needs a `Flow`, (usually) a `@Volatile current*` snapshot for synchronous playback reads, a collector in `init`, and a setter. Keys include `LIBRARY_FOLDER`, `IMPORT_STRUCTURE` (`""` = not chosen → first-run prompt), `APP_THEME` (`""` = not chosen → first-launch theme prompt) / `THEME_COLOR_SOURCE`, `HOME_VIEW_MODE`, `PLAYER_SHOW_SERIES_COVER`, `SKIPPED_UPDATE_VERSION`, skip/rewind/skip-silence config, `DEFAULT_AUDIO_PRESET_ID`, `WIDGET_DEFAULT_COVER_PATH`, `LAST_OPEN_BOOK_ID`, `LAST_PLAYED_BOOK_ID`, `GEMINI_API_KEY`.

### Scanner (`data/scanner/`)

`AudioFileScanner.scanDirectory` dispatches on the user-selected `ImportStructure` (read via `settings.importStructure.first()`):
- **`AUTO`** — the heuristic `scanFolder`: embedded ALBUM tags win (≥2 distinct albums → one book each; one shared album → one book), else `clusterBySimilarName` (filename-stem clustering, splits only on ≥2 genuine ≥2-file sequences), plus single-file volume splitting and disc-split-folder merging. Multi-book folders get a synthetic `"<dir>::<stem-or-album>"` `folderPath` — never `File()` it without checking for `::`.
- **`AUTHOR_SERIES_BOOK`** (`root/author/[series/]book/files`) and **`AUTHOR_DASH_SERIES_BOOK`** (`root/(author - series)/book/files`) — explicit structured walkers; every audio-bearing folder is exactly one book, its files are the chapters (no tag splitting), and it resolves/creates a `Series` for `seriesId`.

Every scan also runs **`reconcileAgainstDisk`**: missing files are dropped (chapters rebuilt), and a book whose files are all gone is hidden (`isIgnored = true`, progress kept) rather than deleted. Guarded so a revoked permission can't mass-hide the library. **`LibraryRestructurer`** (`data/files/`) is the inverse: it moves each book folder to the target computed from the chosen structure + effective author/series, via **copy → verify (file set + sizes) → update DB paths → delete original** (so an interrupted move never loses data), then removes now-empty folders. Chapters: `ChapterExtractor` hand-rolls an MP4 `moov/udta/chpl` Nero-atom reader; `buildChapters` uses embedded markers or one row per file.

### Playback (`playback/`)

**`PlaybackService`** — Media3 `MediaSessionService` owning the single `ExoPlayer`, with a `LoudnessEnhancer` + `Equalizer` that must live on the real ExoPlayer audio session (custom `SessionCommand`s `CMD_SET_BOOST`/`CMD_SET_EQ`). The `MediaSession` is fed a `ForwardingPlayer` whose next/previous seek by time; keep the direct `exoPlayer` ref for effects (do not cast `mediaSession.player`).

**`PlayerController`** (`@Singleton`) — app-side `MediaController` wrapper exposing `PlaybackState`. Syncs in `playerListener` + a 500 ms **position ticker that must run on `Dispatchers.Main`** (MediaController is main-thread-only). `playBook(..., seriesId, seriesBookIds)` carries series-continuation context; on `STATE_ENDED` it marks the book finished and, if in a series, invokes `onSeriesBookEnded` and emits `seriesAdvanced`.

**Damaged files** — a download-damaged MP3 carries runs of garbage (measured: 8 gaps of ~300 KB each through one 7.8 h file). ExoPlayer's `Mp3Extractor` abandons a file after searching `MAX_SYNC_BYTES` = **128 KB** for a valid frame, and Android's own `MediaExtractor` was measured stopping at the same damage — so no demuxer choice and no amount of seeking past "the" gap helps. `Mp3DamageScanner` locates every damaged range and `GapSkippingDataSource` hides them, so the extractor only ever sees a continuous valid stream (`GapMap` holds the logical↔physical arithmetic and is unit-tested). Scanning is a full sequential read (~8 s for 900 MB on desktop), so it runs **only after a file actually fails**, never during a library scan, and the result is cached in `AudioFile.damageRangesJson` (null = never scanned, `""` = scanned clean) and applied up-front by `PlayerController.buildMediaItem` on every later play. The older head-only `SkipHeadDataSource` remains for the corrupt-header retry that fires before a scan has run.

**Series playback is the normal book player, one book at a time** (`playback/SeriesPlayer.kt`, a `@Singleton`): it plays the resume/tapped member as a plain book with the series context; when a book ends, `onSeriesBookEnded` loads and plays the next member, and `PlayerSheet` follows into it (`controller.follow(bookId)` re-targets the open player via the `seriesAdvanced` flow). So there is **one player UI** for books and series. `playSeriesBookAt` jumps to a chapter in another member book (from the whole-series chapter list). `AudioCascade` (`playback/AudioCascade.kt`) resolves the effective speed/boost/EQ/skip-silence and auto-rewind at play time — one shared entry point used by `PlayerViewModel.play()`, `HomeViewModel.playResumeBook()`, `SeriesPlayer`, and the cold widget-tap resume in `PlaybackService`, so a book behaves the same no matter which of those started it.

### UI (`ui/`)

Single-Activity (`MainActivity`) with a Compose `NavHost`. Routes: `home`, `settings`, `search`, `author/{authorName}` (Series has no route — see below); the full player lives in a persistent draggable **`PlayerSheet`** (its own nested NavHost, route `player?bookId=`). Cold start restores the expanded player from `LAST_OPEN_BOOK_ID`, or — if the app was closed with only the mini bar showing — restores the collapsed mini bar from `LAST_PLAYED_BOOK_ID` (`PlayerSheetController.restore`, loads paused). The mini bar is hidden on the `settings`/reader/widget-editor/widget-gallery routes (`PlayerSheet(hideMiniBar=…)`), and a firm downward fling on it calls `PlayerController.stop()` to close the book.

- **Theme** — two looks chosen on first launch (and in Settings → Theme), driven by `AppTheme` + `LocalAppTheme` (`ui/theme/AppTheme.kt`): **Material You** (opaque tonal M3; colors from the system wallpaper on API 31+, or the cover, per `ThemeColorSource`) and **Immersive** (the blurred full-screen cover behind translucent screens, with all text accent-tinted). `VoyageTheme(appTheme, colorSource, coverArtPath, coverAccentOverride)` in `MainActivity` applies it and stays a single entry point (the `when(appTheme)` there is scheme *selection*, not UI structure). The cover-derived accent is normally picked by a swatch fallback chain (`CoverTheme.recolouredFrom` for Immersive, `extractThemeColor` for Material You/COVER), which is why the same cover can theme differently across devices — each `?:` is a hard switch to a different swatch category. `coverAccentOverride` pins a colour instead — one of the cover's own quantized swatches, or anything at all mixed in `ColorPickerPanel` — keyed by cover path in the `cover_accents` preference (`CoverAccentCodec`), surfaced by the “Cover accent” card in Look and feel and read via `LocalThemeCoverPath` + `rememberCoverSwatches` (`ui/theme/CoverAccent.kt`). The card's **“Use on every book”** checkbox writes the separate `global_accent` preference, which `MainActivity` resolves *first*: while it is set the whole library takes that one colour, over every per-cover pin and both automatic pickers. Unticking it restores the per-cover map, which is deliberately never cleared while the override is on. Both ride the settings mirror to `settings.json`, so they survive a reinstall.
  - **UI split convention**: every screen/component that visually differs between the two looks has a fully separate implementation per theme, in `ui/material/**` and `ui/immersive/**` (mirroring the original package structure, e.g. `ui/material/player/PlayerScreen.kt` / `ui/immersive/player/PlayerScreen.kt`). The file at the *original* path (e.g. `ui/player/PlayerScreen.kt`) becomes a thin `when (LocalAppTheme.current) { AppTheme.IMMERSIVE -> ...; AppTheme.MATERIAL_YOU -> ... }` router with the same public signature — this is what everything else in the app keeps calling, and it's what preserves the nav back stack, route-scoped ViewModels, and the PlayerSheet's persistent state across a runtime theme switch. Per-variant color constants live in `ui/material/MaterialStyle.kt` / `ui/immersive/ImmersiveStyle.kt` (the old shared `immersive()`/`appSurfaceColor()`/`appCardColor()`/`appCardHighColor()`/`scrimTextColor()` helpers are gone).
  - **Shared sheets/overlays/utilities stay unsplit** (`PlayerSheet`, `BookOptionsSheet`, `ChapterSheet`, `AudioSettingsSheet`, etc., and cross-cutting primitives like Settings' `NavRow`/`CardContainer`) — they have no visual branching today. Split one on demand with the same router recipe the moment it needs to diverge; don't split ahead of need. When splitting, note that `ImmersiveStyle.scrimText`/`cardColor` are for content drawn over the blurred cover, **not** for content inside a sheet: a sheet sits on `appSheetColor()` (`surfaceContainerLow`), which is light under a light scheme, so it needs `onSurface`/`surfaceContainer*` or the text comes out invisible. (The companion used to be this section's worked example of a router — `ui/companion/CompanionSheet.kt` over `ui/immersive/companion/` and `ui/material/companion/`. It is now an example of the *opposite* bullet: see the companion deck below.)
  - **The inverse also applies: when two screens are copies of each other, share the frame instead of the router.** Book Info and the Series page are the worked example — they were four near-identical files (book/series × immersive/material), so a visual change had to be made four times and drifted when it wasn't. They now share **one** page implementation: `ui/components/InfoPageScaffold.kt` owns the non-visual half (cover morph out of the tapped grid card, `CoverBoundsRegistry` registration, predictive back) and routes to `ui/immersive/components/InfoPageFrame.kt` / `ui/material/components/InfoPageFrame.kt` for the look. `ui/bookinfo/BookInfoScreen.kt` and `ui/series/SeriesDetailScreen.kt` are single, theme-agnostic implementations that pass in only what genuinely differs — an `InfoPageData`, their overflow items, and slots for anything below the panel (the Series page's swipe-up pill) or over the page (its books panel). **Change the page once, both screens follow.** Per-theme fills that the callers still need (the books panel, its rows, dialogs) resolve inline against `LocalAppTheme` the way `appSheetColor()`/`appDialogColor()` in `ui/components/SheetStyle.kt` do — not by re-splitting the screen.
  - **The companion deck is the second worked example of that, and the reason the old router was deleted.** `ui/companion/CompanionDeck.kt` is one implementation of a four-band full-screen surface (header / spine / pane / dock, plus a two-column landscape variant), and `ui/companion/CompanionDeckStyle.kt` is its per-theme half — fills, shapes, and the two leaves where the component genuinely differs (`DeckSpine`: a glass segmented pill vs an M3 tab row; `DeckDockSurface`: a floating borderless slab vs a seated tonal bar). Everything else — the four panes in `CompanionPanes.kt`/`CompanionMapPane.kt`, the portrait ladder in `CompanionPortrait.kt`, the dock in `CompanionDock.kt` — is theme-neutral and reads its colours from that token file. The map pane pans and zooms: the board artwork is transformed by a `graphicsLayer` with a top-left `TransformOrigin`, and pins are transformed by hand through `mapToScreen`/`screenToMap` rather than by sharing that layer — which is what keeps a marker the same size and the same tap target at 1x and at 5x, and what lets an edit-mode pin drag divide out the zoom instead of moving the pin by several times what the finger moved. `CompanionSheet.kt` (all three), `CastStrip.kt`, `PackBoardScreen.kt` and `CompanionEditorSheet.kt` are gone.
  - When `PLAYER_SHOW_SERIES_COVER` is on and the playing book is in a series, the theme (and player backdrop) use the **series** cover.
  - When nothing is actively playing, the theme falls back to the cover of `SettingsStore.themeBookId` — set alongside `lastPlayedBookId` wherever a book actually opens/plays, but (unlike `lastPlayedBookId`) never reset on `PlayerController.stop()`, so closing a book keeps its theme until a genuinely different book is opened, instead of reverting.
- **Home** (`ui/home/`) — the library grid runs **under the status bar** (the Scaffold's top inset is re-applied as the grid's own `contentPadding`, and explicitly to the two things that are not the grid: the empty-library screen and the floating selection bar), so `Modifier.topEdgeFade` (`ui/components/TopEdgeFade.kt`) can blur and dissolve the top band at the physical screen edge instead of leaving covers guillotined by the grid's own clip. The blur is a stack of four increasingly-blurred bands re-recorded from one captured `GraphicsLayer` — never from `drawContent()` per band, which would re-run the whole grid's draw pass four extra times every scrolled frame — and needs API 31 (`BlurEffect`); below that the alpha ramp carries the effect alone. A **Books / Series / Authors** view switch (`HomeViewMode`, persisted). `HomeViewModel.buildGridItems` groups `HomeGridItem.{SingleBook,SeriesItem,AuthorItem}` per mode; per-view covers resolve `Series.coverArtPath` / `AuthorMeta.coverArtPath` / book cover. **Multi-select**: long-press any card (books, series, authors — mixed) toggles a typed `SelKey` selection; the selection bar offers Delete (series/authors cascade to all member books, with a delete-files toggle), Add-to-series (1 series + books → adds them and opens the series manager), and a single-selection ⋮ overflow (cover search + book options). A book card's play button starts playback in place (`playResumeBook`) without opening the full player. Status tabs (All/Listening/Not started/Finished) + resume card as before.
- **Series screen** (`ui/series/SeriesDetailScreen`, keyed by `seriesId`) — a manager: Play series, add/remove/reorder/rename, and **Series options** (`SeriesOptionsSheet`: speed/boost/skip-silence/author/narrator). Tapping a member plays the series from that book (`openPlayer` event → `sheetController.open(bookId)`). Its page frame is literally Book Info's — see `InfoPageScaffold` under the theming section — so it contributes only the books panel, the overflow items and the swipe-up affordance. It has **no NavHost route** — `SeriesOverlayController`/`SeriesOverlay` (`ui/series/SeriesDetailScreen.kt`) host it as a persistent overlay drawn above Home (its own tiny nested NavHost, mirroring `PlayerSheet`'s Book Info recipe), not a destination that replaces Home — its cover-morph open/close animation (`CoverBoundsRegistry`, same primitives as Book Info) needs the tapped library grid card still composed underneath it, which a real nav destination tearing Home down would have broken. `ui/author/AuthorDetailScreen` lists a (effective) author's books.
- **Player morph (Material You portrait)** — the mini bar → full player transition is data-driven: `ui/player/ElementMotion.kt` defines `ElementMotion` (per-element slice of progress, easing, travel path, scale mode, anchor, alpha window, radius) and `Modifier.elementMotion`, with the authored values in `PlayerChoreography`. It replaces `morphFrom`/`expandReveal` **only** in `ui/material/player/PlayerScreen.kt`'s portrait body; Immersive and both landscape layouts still use the original modifiers, which are unchanged. Three things it adds that the old modifiers cannot express: a **bounce group** (`MorphBounceGroup` — the cover/title/author/play button absorb the driver spring's overshoot as one rigid scale about their shared centre, instead of each bouncing along its own travel vector), **spawn rules** (`Spawn.UncoveredBy` reveals a transport button once the travelling play button covers enough of it; `Spawn.SlideOutFromPlay` slides the left-hand buttons out from under its resting position; `Spawn.DropFromBehindCover` drops the chapter pill out from behind the cover, which is why the cover Box carries `zIndex(1f)`), and **arc paths** (`MorphPath.ArcVerticalFirst` — the play button rises before sweeping left; on a straight line it arrives from below and covers nothing). Material You's sheet spring is deliberately bouncier (0.60/380, set in `PlayerSheet`) than the shared `MotionTokens.floatSpatial` — the sanctioned exception to AN-11, since the rebound *is* the design and it is scoped to one theme. Authored in `docs/motion-lab.html` (a browser page, no build required) and recorded in `docs/motion-spec.md`; change values in both places together.
- **Player** (`ui/player/`) — full-bleed cover backdrop (`ReflectedProgressiveBlurCover` + baked `CoverEffectBaker` WebP in `filesDir/cover_fx/`). Overflow menu has a book↔series **cover toggle** when the book is in a series. The chapter list (`ChapterSheet`/`ChapterOverlay`) spans **all member books** when a series is playing (headers per book); tapping a chapter in another book switches to it. Internally it maps `ChapterRow` onto a private `ChapterListRow` that adds per-book numbering, group id and timeline ordinal — which is what makes search (title *or* chapter number), header-drops-when-empty, and “already played” dimming cheap. Long lists get a drag rail (>20 rows) and a “Now playing” jump pill. **Haptics** (`ui/haptics/`) — `Feel` is the app's vocabulary (Tap/Select/ToggleOn/ToggleOff/Grab/Release/Step/Boundary/Reveal/Dismiss/Commit/Warn/LongPress/Transport), resolved to platform `HapticFeedbackConstants` by strength and API level; `View.performHapticFeedback` only, never a raw `Vibrator`, so there is no `VIBRATE` permission and the system setting always wins. Coverage is two-layer: `VoyageIndication` is provided as `LocalIndication` and fires `LocalPressFeel` on every bare `Modifier.clickable`; the Material components build their own `ripple()` and ignore that local, so call sites use the `Haptic*` wrappers in `HapticControls.kt` instead (~307 sites converted). Each wrapper provides `LocalPressFeel = null` so it cannot double-fire. A region whose presses mean something else wraps itself in `PressFeel(Feel.X)` rather than editing every control inside it. The seek bar has five designs and is a user choice in **both** looks (`ScrubberStyle` + `drawScrubber` in `ui/components/ScrubberArt.kt`, provided as `LocalScrubberStyle`): the shared `VoyageScrubber` (`ui/components/VoyageScrubber.kt`) owns the gesture, swell spring, haptics and hit target for all of them and delegates only the paint, which is also what lets Settings preview each option with the real drawing code. Each style declares its own height. `CLASSIC` is the exception the composable-level branch exists for — it renders the real M3 `Slider` rather than a Canvas repaint of one, because those visuals belong to Material and a hand-drawn copy would drift from it on every library update. The four painted designs were Immersive-only and the Material slider was Material You-only; nothing in either was theme-specific, so both players now call `VoyageScrubber` (portrait and landscape, chapter and whole-book). The two looks keep **separate preferences** (`scrubber_style` / `scrubber_style_material`) purely so each retains the default it shipped with; `MainActivity` picks between them by active theme, so nothing downstream knows which one fed the local. The Immersive mini player cover has two shapes (`MiniCoverStyle`, provided as `LocalMiniCoverStyle` from `MainActivity`): `CAP` (the pill leading edge, progress via `PillPerimeterProgress`) and `RING` (an inset disc, progress as a ring). The shape changes the morph, not just the paint — `PlayerExpandTransition.coverSourceIsCircle` switches the Immersive player from `morphFrom` to `morphFromCircle`, which uniform-scales by the shorter side and clips through an interpolating circular window, because a circle and a full-bleed cover share no aspect ratio.
- **`ReaderPageView` takes `fillHeight` explicitly — never infer it from the constraints.** The reader's page IS the viewport and must fill it; the reading-settings preview must shrink-wrap its sample. The old code inferred "bounded height means fill it", which is true of the reader and false of a preview sitting in a plain `Column` (a Column hands non-weighted children a bounded height). The preview therefore took the whole screen and pushed the scope row, the six tabs and every control off the bottom — Reading settings opened looking like a page of sample text with no settings on it. Bounded-ness says how much room there is, never what the caller wants done with it.
- **The reader reserves the chrome's MEASURED height, and its gesture callbacks are read through `rememberUpdatedState`.** Two bugs with one shape — trusting a value captured at the wrong moment. (1) `chromeTop`/`chromeBottom` were computed as `statusBars + 64dp`, but the reader runs fullscreen (so `statusBars` is 0) while `TopAppBar` sizes itself with `TopAppBarDefaults.windowInsets`, which includes the display cutout: on a punch-hole phone ~29dp of every page hid behind the bar at each end, and since the paginator had been told the page was taller than it is, those lines were never pushed to the next page. Both bars now report their height through `onSizeChanged` and the reservation follows them; a remembered value is only replaced by a real measurement, so toggling the chrome does not repaginate. (2) `readerGestures` built its `pointerInput` blocks keyed only on the settings, so they started once and kept the first `onTurn` — which closed over the pages list from before pagination ran. With `pages.lastIndex == -1` every turn fell through to `onNextChapter()`/`onPrevChapter()`, so taps and swipes skipped whole chapters and never turned a page. **Any callback captured inside a `pointerInput` whose key does not change with it must go through `rememberUpdatedState`** — same trap as `VoyageScrubber`.
- **A widget button must be a foreground-service start.** `WidgetIntents` uses `PendingIntent.getForegroundService`, never `getService`: a plain `startService` at a process that is not running is refused by the platform on API 26+, silently and before any app code runs, which is exactly "the widget does nothing when the app is closed". The obligation that comes back with it is that `startForeground` MUST happen within ~5 s, and the cold path (read last-played id → load files → prepare → play) is asynchronous and can legitimately end without ever playing. So `PlaybackService.promoteForColdWidgetTap` posts a placeholder immediately **under Media3's own notification id and channel** — Media3's real notification then replaces it instead of joining it, and we never have to call `stopForeground` on a service Media3 has since promoted. **Any new widget action inherits both halves of this.**
- **Scrolled mode reads a chapter WINDOW; paged mode reads one chapter.** The two surfaces own position in opposite directions and that is deliberate. Paged mode owns a page index and the ViewModel follows it. Continuous mode stacks the previous/current/next chapters in one `LazyColumn` — so a chapter boundary is a paragraph break, not a wall — and the *list* owns the position, reporting `(spineIndex, renderStart)` to `onScrolledTo`, which commits a crossing without recording a skip because nothing was skipped. Two rules keep the seam invisible and both are load-bearing: **list keys must be `spineIndex:renderStart`** (`renderStart` is unique only within a chapter, and Compose re-finds the first visible item by key, which is what stops a window rotation from moving the page), and **`refreshScrollWindow` must start from the chapters already on screen**, never rebuild from the centre out — doing the latter empties the list to one chapter for the length of a parse and the text above and below the reader visibly disappears. `ScrollAnchor`'s generation is what separates "a jump told me to move" from "the window rotated under someone who is just reading"; only the former re-anchors.
- **A reader mark anchors to a block, never to a page or a character range.** `reader_marks` stores `renderStart`, which is a property of the document; page numbers are a function of font, size, margins, columns and rotation, so a mark stored as "page 41" moves to a different paragraph the moment any of those change. Marks also carry `textFraction` (the extractor-stream coordinate `jumpToSpine` takes) because following a mark into a chapter that is not loaded cannot resolve a render offset — that document is not in memory. **One coordinate is for drawing, the other is for travelling; a new mark type needs both.**
- **Reader chrome is navigation, not decoration.** The reader's `TopAppBar` carries the only routes to Contents, to Reading settings and back out of the book, so its visibility is gated on `chromeVisible` **alone**. It used to also require `prefs.showHeader` — a switch inside Reading settings — so turning it off bricked the reader: no bar, and therefore no way to reach the screen that could turn it back on. `showHeader` now chooses between the full bar and `ReaderNavCluster` (the same three destinations as floating buttons), never between a bar and nothing. The same trap existed in gestures: `fullscreenTapTurns` routes every tap to a page turn, so the centre-tap chrome toggle was unreachable and hidden chrome could not be brought back — `readerGestures` now binds `onLongPress` to `onToggleChrome` unconditionally as the escape hatch. **When adding a reader setting, check it cannot hide its own way back.**
- **Updates** — `ui/update/UpdateGateViewModel` checks once per launch and shows `UpdateAvailableScreen` (Install / Skip; Skip records `SKIPPED_UPDATE_VERSION` so only that version is suppressed). The manual checker in Settings → About is separate.
- Cascade-of-data caveat: because grouping/queries are override-aware, changing an author/series in the app is reflected live; a `Book.author`-based grouping would not be. Use `displayTitle`/`displayAuthor`, never raw `title`/`author`.

### App icon

Adaptive icon (`mipmap-anydpi-v26/ic_launcher*.xml`): a gradient background `@drawable/ic_launcher_background*` + a raster foreground `@mipmap/ic_launcher_fg*` at 5 densities. **Whatever a layer contains, it is a 108dp canvas of which the launcher shows only the middle 72dp** — art placed at full size loses a third of every edge. Two families live here and they follow opposite rules:

- **The six sailboat colourways** share one mark (`ic_launcher_fg`) over swappable backgrounds, so **their foreground must stay transparent outside the mark** — it is drawn over the background at the same size, and an opaque one hides it entirely. The original export was the complete icon (sailboat *on* an opaque navy square), which silently made the background layer dead weight and forced every variant to render identically navy; `scripts/gen_launcher_fg.py` stripped that baked-in navy out and documents the method.
- **The Vee family and Voyager** are whole authored icons — ground included — so each brings its own opaque foreground and there is nothing to swap underneath. `scripts/gen_launcher_fg_from_art.py` turns a finished square PNG into that pair: it places the art at 72/108 so the visible result matches the source file, and pushes the artwork's own ground out to a full square, discarding its rounded corners and border rim (otherwise the launcher masks a rounded square that already has rounded corners, and the icon reads as a small tile floating inside a bigger one). It does the flattening geometrically on purpose: on an export whose surround is the same colour as its ground, edge detection finds the *mark* instead and floods that across the row. Optional hue-shift/saturation args generate the recolourways from one source file.
- **The flat colourways of both marks** go back to the conventional split, and are the counter-example to the bullet above: `scripts/gen_launcher_flat.py` keys the mark off its near-black ground by luminance at the source’s full resolution, fills it with one ink and centres it at 54/108, leaving the rest of the foreground transparent so the solid-colour background layer genuinely is the icon’s ground. Three things it gets wrong if you rush them: **the cut has to be low** (55, not 95 — the V's stacked page edges, and Voyager's sail, star and trail, all live between ~40 and ~95, and a threshold set safely above the ground welds the page layers into one wedge and erases the sail entirely), which means the ground's own corner glow leaks in and has to be removed *structurally* — `clear_frame_connected` erases whatever touches the frame, since the glow always reaches the edge and the mark never does — followed by a 3px opening for the anti-aliasing crumbs (5px severs the page strokes). **Resize the mask and paste ink through it**, never fill then downsample, which blends ink with the transparent surround and rings every edge with a halo. And **54/108 is not a taste call**: it is both the authored proportion (each mark is ~0.74–0.82 of its own tile, so anything larger is a crop of a different composition) and the circle-mask limit (the bounding box's diagonal is ~1.27× its long side, so past ~56 a circular launcher cuts the V's outer page strokes off).

Verify a variant actually renders rather than assuming the wiring is enough — both scripts print what they did, and the second's output can be composited offline instead of costing a build and an install per look.

The user can switch the launcher icon among twenty-six variants (Settings → Look and feel → App icon; `util/AppIconManager.kt`). They are grouped into three `IconStyle`s (Vee, Voyager, Classic), and the picker is two-step: choose a style, and that style's colourways expand below it in a wrapping grid. **Enum declaration order groups the styles and orders the colourways inside each** — `IconStyle.icons()` filters the one list rather than keeping a second one, so adding a variant means adding one row. Each variant is an `<activity-alias>` in the manifest targeting `MainActivity`, toggled with `setComponentEnabledSetting` — **always passing `PackageManager.DONT_KILL_APP`**, since that call otherwise kills the process mid-sequence and can leave two enabled launcher icons or none at all. `PackageManager` is the sole source of truth for the active icon (not mirrored into `SettingsStore`). The settings preview paints each variant's gradient from colours duplicated in the `AppIcon` enum — keep those in sync with the background drawables — and scales the foreground by 108/72 so it predicts the launcher instead of previewing every mark a third too small.

**The default is VEE**, set by `android:enabled="true"` on exactly one alias plus that entry's `manifestDefaultEnabled`; `<application android:icon>` matches it, so Settings → Apps and the task switcher agree with a fresh install's launcher icon. Moving that default is not additive: on an install where the user had explicitly chosen another variant, their alias is `COMPONENT_ENABLED_STATE_ENABLED` while the newly-defaulted one is still `COMPONENT_ENABLED_STATE_DEFAULT` — which now resolves to true, so **both** are enabled and the launcher shows the app twice. Aliases added in a later version are invisible to the `apply()` call that ran before they existed, so it cannot be fixed where the user picks an icon; `AppIconManager.reconcile()` runs from `VoyageApp.onCreate` and collapses any such conflict, preferring an explicitly-enabled alias over a manifest-default one.

### Widget maker v2 & AI

The home-screen widget (`widget/`) is a single free-size `VoyageWidgetProvider`, driven entirely by `WidgetUpdater` (`@Singleton`) — no exported broadcast: `PlaybackService.pushWidgetState()` builds a `WidgetSnapshot` (`widget/model/`) and calls `widgetUpdater.push(...)` directly, which persists it via `WidgetStateStore` (its own DataStore file, so a cold-started widget — reboot, launcher restart — always has real data instead of rendering blank) and calls `AppWidgetManager.updateAppWidget` itself. The 1 Hz sleep-timer tick calls the lighter `widgetUpdater.tickCountdown()` (re-renders only widgets whose design shows a countdown) rather than a full state push, except in END_OF_CHAPTER sleep mode which has no fixed deadline to self-correct from. **The placed widget only re-renders when the editor's Save button is tapped** (it calls `widgetUpdater.requestRender()`) — changes made in the editor are NOT pushed live as you drag sliders, only on Save (which now also shows a "Widget updated" Snackbar as an explicit confirmation a push was attempted). On some OEMs (OnePlus/ColorOS confirmed) aggressive background-process restrictions can still drop or delay that `updateAppWidget` call if the app's process gets frozen — not fixable from app code; the user needs to disable battery optimization / enable autostart for the app if a placed widget seems stuck on stale data.

A design (`data/db/entities/WidgetDesign.kt`, table `widget_designs`) is a `WidgetDesignDoc` (JSON, `widget/model/WidgetDesignDoc.kt`) — a z-ordered list of freely-positioned `ElementSpec`s in a fixed **design-unit space** (`CANVAS_UNITS = 1000` wide, `1000/aspectRatio` tall), so `w == h` is always a true square regardless of the design's own aspect ratio or the real granted pixel size. There is no separate fixed "background" field: a design starts genuinely blank, and the user's first step is adding a `BACKGROUND_LAYER` element from the picker. **The widget bitmap itself is always a plain rectangle** — a `BACKGROUND_LAYER` element (there can be zero, one, or several) is an ordinary element like any other: movable, resizable, rotatable, with its own `shapeKind`/`cornerRadius` (rect/pill/circle/squircle) clipping only its own fill, never the whole bitmap. A newly-added background just defaults to a full-bleed rect at the bottom of the stack (`WidgetEditorViewModel.addElement`) so the common case still looks the same as before — it's just editable now instead of a special-cased "base layer". `WidgetDesignCodec.decode(json, aspectRatio)` transparently migrates designs saved before either the background-as-element change or this rectangle-only change (a top-level `"background"` JSON key) into a synthetic full-bleed `BACKGROUND_LAYER` element — no Room migration involved, since `documentJson` is opaque TEXT; the `aspectRatio` param (from the owning `WidgetDesign` row) sizes that synthetic element's height correctly now that it's rendered at its own stored bounds instead of being force-filled by the painter.

`WidgetPainter.paint(...)` is the single pure `(doc, aspectRatio, snapshot, sizePx) -> Bitmap` function shared verbatim by the provider, the editor's live canvas (`ui/widget/EditorCanvas.kt`), and every thumbnail (gallery, configure picker) — the editor preview IS the widget render, byte-for-byte. Accent color (for `usesAccent` icon/text tints) is resolved from whichever `BACKGROUND_LAYER` element actually shows a cover image, falling back to the snapshot's own book/series cover if none does. Where no real cover is available at all (an element's own image lookup, or the accent-source lookup) the painter draws the app's own launcher icon (`R.mipmap.ic_launcher`) as the placeholder — not a separate drawable. `WidgetBinding` (table `widget_bindings`) maps a placed `appWidgetId` to a design; `WidgetUpdater` handles orphan-binding GC, `onRestored` id remapping (launcher backup/restore), and re-rendering bound widgets as a "pick a design" placeholder when their design is deleted.

Tap handling can't use RemoteViews' per-view positioning below API 31 (minSdk 26), so `widget/HitGrid.kt` overlays a static 12×12 grid (inlined directly into `res/layout/widget_host.xml` — no `<include>`, and cells are `ImageView`, the only bare view RemoteViews reliably inflates in the launcher process — generated by `scripts/gen_hit_grid.py`) and assigns each interactive element's PendingIntent (`widget/WidgetIntents.kt`) to the cells its rendered rect actually overlaps (topmost z wins ties) — bounding tap error to about half a cell. TEXT/IMAGE/SHAPE/BACKGROUND_LAYER elements can also carry a `TapAction` (play/pause, open player, skip, etc.), making a cover, title, or background interactive too, not just dedicated control icons. A `PROGRESS_BAR` shape element can render as a `LINE` (the original horizontal bar), or as progress sweeping around a `RING`/`SQUARE`/`ROUNDED_SQUARE` outline (`ShapeStyle.progressShape`/`strokeWidth`) — the perimeter fill is drawn by walking `fraction * length` of the outline path via `android.graphics.PathMeasure`, one recipe for all three non-line shapes (`WidgetPainter.drawPerimeterProgressBar`).

The editor (`ui/widget/WidgetEditorScreen.kt` + `WidgetEditorViewModel.kt`) is a photo-editor-style workspace, not a form: free-placement (no snapping); a single stationary full-canvas gesture layer (`ui/widget/SelectionOverlay.kt`) picks move/resize/rotate by where a drag starts, since per-handle gesture detectors on small elements used to blanket the whole touch area. There are **no modal sheets** — `ElementPickerPanel`/`LayersPanel`/`ElementOptionsPanel` are plain composables docked persistently below the canvas (`EditorDock`, a tab row for Elements/Layers/Options plus Copy/Delete/Collapse acting on the current selection), so nothing ever covers the canvas; selecting a new element auto-switches the dock to Options. The canvas (`ui/widget/EditorCanvas.kt`) is a pannable/zoomable **workspace** — a "pasteboard" filling nearly the whole screen — containing the widget frame (always a plain rectangle, with a dashed outline tracing its real bounds, editor-only) as a rectangle the user can zoom out to see floating in the workspace, zoom in past its edges, or pan anywhere; the checkerboard (transparency indicator) is confined to the frame's own bounds, not the whole workspace. Pinch/pan is a two-finger-only `pointerInput` on the workspace root so single-finger element drag/tap is untouched; double-tap resets zoom/pan. Tap-to-select/deselect hit-tests every element uniformly now that backgrounds are ordinary elements. `ui/widget/AlignmentGuides.kt` draws purely visual center/thirds/edge hints during a drag that never move the element. `ui/widget/WidgetGalleryScreen.kt` is the design library (replaces the old inline Settings list); Settings → Widget now just links to it. Icons are the `ic_w_*` vector drawables (`widget/render/IconAssets.kt`) — full-bleed, tight glyphs with zero renderer-added padding, unlike the old `ic_*` set; the layers panel and element picker (`ui/widget/ElementPickerSheet.kt`'s `ElementTypeIcon`/`labelFor`) reuse the same glyphs for control types, falling back to representative Material icons for text/image/shape/background types. Image elements can lock their width/height ratio (`ImageStyle.lockedAspect`) so drag-resize keeps a fixed shape instead of stretching freely. `ColorPickerRow` (`ui/widget/ColorPickerRow.kt`), used by every style panel, has a visual HSV picker (hue slider + saturation/value square) alongside the hex/alpha fields, plus a strip of recently-used custom colors (`SettingsStore.widgetCustomColors`/`addWidgetCustomColor`, surfaced via `WidgetEditorViewModel.recentColors`) prepended to the preset swatches — a color picked once on any element is immediately offered everywhere else.

`SynopsisService` calls Gemini via the DataStore-stored `GEMINI_API_KEY` (never hardcode the `AIzaSy...` key). `CoverSearchService` searches online covers and returns raw bytes (`downloadBytes`) — it deliberately does **not** decide where they land, since a cover's canonical location depends on the book's folderKey shape; `BookDataStore`/`LibraryDataStore` own the write (see Storage model).

`SettingsScreen` sections are a `SettingsSection` sealed class dispatched in one `AnimatedContent` `when` (Root, Theme, Library, Playback, Presets, Widget, AI, Updates, About, Diagnostics) — each is a `LazyListScope` extension; adding a section means updating the sealed class, the nav row, the title `when`, and the content `when` together.

## Conventions

- Hilt for all DI; new singletons/DAOs go through `di/AppModule`; ViewModels are `@HiltViewModel`.
- Room/DataStore `Flow` → `stateIn` for reactive UI; one-shot reads via `*Once` repo methods or `.first()`.
- Media3 APIs need `@UnstableApi`; experimental flow operators (`flatMapLatest`) need `@OptIn(ExperimentalCoroutinesApi::class)`; `MutableStateFlow.update {}` needs `import kotlinx.coroutines.flow.update`.
- `LazyListScope` extension "section" functions in `SettingsScreen` receive data as params — don't `collectAsStateWithLifecycle()` in the extension body (do it inside an `item {}`, which is `@Composable`).
